# Мост Meshtastic ↔ Bitchat для Windows

Две разные сети, одна переписка: радио на LoRa (Meshtastic) и телефон
с Bitchat по Bluetooth. Между ними — обычный ПК на Windows, программа
на Python. Интернет не нужен, серверов нет, ничего никуда не регистрируется.

```
LoRa : Meshtastic   ←──  мост на ПК  ──→   Bitchat на телефоне (#mesh)
```

## Что оно делает и чего не делает

Делает:

* **LoRa → Bitchat** — само, сразу, как только радио что-то приняло.
* **Bitchat → LoRa** — руками (`s` в консоли): сообщения копятся в буфере,
  уходят пачкой «последние 5/10/20/50» с паузой между отправками, потому что
  в LoRa нельзя часто и много.
* **Полная синхронизация** — если очень надо, чтобы Bitchat → LoRa тоже
  шло само. Включается в меню и спрашивает подтверждение.
* **Режим пересылки** (`b`) — чьи сообщения из Bitchat вообще имеют право
  уйти в LoRa.
* Показывает, что пришло и что ушло, но **никогда не показывает текст** —
  ни в консоли, ни в логе. Только имя автора и число символов.

Не делает и не будет:

* не читает личные сообщения Bitchat и группы — они зашифрованы ключами
  телефона, а не моста;
* не работает с геочатом — он вообще ходит через интернет-релэи, а не по
  Bluetooth;
* не работает с двумя телефонами сразу — один телефон на запуск, и его
  надо подтвердить руками.

Почему так — ниже, в «Геочат, группы и личные сообщения».

## Что нужно

* Windows 10/11 с рабочим Bluetooth (для телефона).
* Радио Meshtastic. Как подключить — по Wi-Fi (TCP 4403) лучше всего,
  по USB (COM) тоже можно, по BLE только если на радио выключен Wi-Fi
  (на ESP32 они не живут одновременно).
* Телефон с открытым Bitchat рядом с компьютером.
* Python 3.10+ (у автора 3.14).

## Установка и запуск

```bat
install.bat
```

Создаст `.venv`, поставит зависимости из `requirements.txt` и скопирует
`config.example.json` в `config.json`.

Дальше:

* `run.bat` — консольная версия (меню, буферы, всё то же, что в окне);
* `run_gui.bat` — окно на Qt 6 (PySide6), если он установлен.

## Консольная версия

`run.bat` открывает меню выбора радио: Wi-Fi, Bluetooth, USB или адрес
вручную. Дальше — поиск телефонов Bitchat, подтверждение и выбор беседы
(канал или личный чат с узлом).

Мелочи, которые обычно сбивают с толку:

* По Wi-Fi мост сначала быстро опрашивает подсети, потом, если радио мало,
  терпеливее. VPN-адаптеры пропускаются, поэтому включённый VPN не прячет
  радио.
* В списке телефонов могут быть адреса-фантомы: iOS меняет свой
  Bluetooth-адрес, а Windows помнит старые. Мост проверяет каждый адрес и
  оставляет только те, что реально ответили announce с подписью.
* Телефон надо подтвердить два раза `yes`. Это не паранойя ради паранойи:
  иначе один случайный Enter привяжет мост к чужому телефону в аудитории.

После запуска в консоли живут команды:

```
s — синхронизация (направление, 5/10/20/50, период)
b — что пересылать из Bitchat в LoRa
l — состояние буферов и расписания
r — сброс привязки к телефону
q — выход
```

### Синхронизация

**Meshtastic → Bitchat** — автоматически. При переподключении телефона
досылается только то, что ещё не дошло, старое не повторяется.

**Bitchat → Meshtastic** — вручную: `s` → направление → количество → при
желании период повтора. Между отправками в эфир пауза 10 секунд. Слишком
старые сообщения, пролежавшие в очереди, отбрасываются — чтобы не
разгружать вчерашнее.

**Полная синхронизация** — `s` → `3) Полная синхронизация в обе стороны`
→ включить. Каждое новое сообщение уходит сразу, уже накопленное тоже
досылается. Выключается там же. Можно задать в конфиге
(`"full_sync": true`) или флагами `--full-sync` / `--no-full-sync`.

### Что пересылать из Bitchat в LoRa

Клавиша `b`. Правило действует на всё сразу: ручную отправку, полную
синхронизацию и повтор по расписанию.

| меню `b` | кто уходит в LoRa |
|---|---|
| `1) один телефон` (по умолчанию) | только тот телефон, что подтвердили при запуске |
| `2) два телефона` | привязанный + ещё один из списка |
| `3) много телефонов` | привязанный + любой выбранный список |
| `4) любой телефон` | всё, что дошло до моста |
| `5) те, кому я ответил` | привязанный + те, кому вы сами ответили в `#mesh` |

Пункты `2` и `3` — один режим (`custom`), разница только в том, сколько
телефонов вы отметили. Перед `2`–`5` мост предупреждает и просит два `yes`.

Про `5` отдельно, потому что он хитрее остальных: в общем чате нет
адресата, поэтому «ответил человеку» на проводе выглядит только так —
сразу после его сообщения в `#mesh` ушло сообщение с вашего телефона.
Мост запоминает этого человека и дальше его сообщения тоже идут в LoRa.
Пока не ответили — не идут. Текст для этого не читается, только порядок.
Список живёт до перезапуска и на диск не попадает.

Что именно гарантируют режимы — не гарантируют:

* В `1` принимаются пакеты только от привязанного пира и только с
  проверенной подписью.
* В `2`, `3` и `5` выбранный пир «доверен» своим announce, но если его
  ключ известен, подпись каждого пакета всё равно проверяется.
* В `4` подпись обязательна для всех, чьего ключа мост уже знает; по одному
  peer id принимается только незнакомый пир.
* Сообщение, собранное из фрагментов, приходит без подписи — автора такого
  сообщения проверить нельзя.
* Имя автора берётся из announce. У совсем незнакомого пира будет `@a1b2`.

Режим записывается в `config.json` (`"bitchat_forward"`), поэтому
переживает перезапуск. А вот списки телефонов и ответивших — нет: после
старта `custom` и `replies` начинаются заново как `bound`. Так
подправленный кем-то конфиг не может тихо расширить пересылку.

Из командной строки: `--bitchat-forward bound|custom|replies|all`.

### Имя автора в LoRa

В LoRa каждое сообщение из Bitchat уходит с именем в начале:

```
[Бит: Имя] текст
```

Имя берётся из announce. Переносы строк и квадратные скобки из него
вычищаются, длина ограничена 32 символами — чтобы чужое имя не могло
подделать строку протокола или занять весь пакет.

### Адресация прямо из Bitchat

| что написать | куда уйдёт |
|---|---|
| `привет` | в выбранный чат по умолчанию |
| `#1 привет` или `/c1 привет` | в канал 1 |
| `/dm A1B2 привет` | лично узлу `A1B2` |
| `/dm !a1b2c3d4 привет` | лично по id узла |
| `/ch` | мост пришлёт список каналов радио |
| `/help` | краткая подсказка |
| `/sync` | напомнит, как открыть меню синхронизации |

Команды (`/ch`, `/help`, `/sync`) слушаются только от привязанного
телефона. От чужого — молча игнорируются.

Ответы моста приходят от пира `MeshBridge` с префиксом `[Bridge]`.
Входящие из приватного канала помечаются `[Mesh: имя / Канал]`,
личные — `[Mesh DM: имя]`.

### Смена телефона

Привязка живёт до конца работы моста. Чтобы перейти на другой телефон:
`r` в консоли, два `yes`, затем `q` и запуск заново — новый телефон надо
подтвердить с нуля.

## Окно: что где

* **Обзор** — жив ли мост (пульс), обе связи, сколько чего ждёт и ушло,
  когда была последняя пересылка.
* **Пересылка Bitchat → LoRa** — те же пять режимов, что `b` в консоли,
  и список телефонов рядом с галочками.
* **Синхронизация** — кнопки «отправить на телефон / в LoRa», полная
  синхронизация, повтор по расписанию.
* **Подключения** — радио, беседа, телефон, отпечаток ключа, сброс привязки.
* **Журнал** — то же, что консольный вывод, без текста сообщений.

Два подтверждения консоли в окне стали двумя диалогами подряд. Смысл
тот же: расширяющее доступ решение не должно срабатывать от одного
случайного клика.

## config.json

```json
{
  "name": "MeshBridge",
  "chat": {
    "kind": "channel",
    "index": 0
  },
  "ble_scan_seconds": 3.0,
  "bitchat_target": "",
  "full_sync": false,
  "bitchat_forward": "bound",
  "history_limit": 100,
  "lora_send_interval": 10.0,
  "lora_stale_seconds": 1800,
  "log_file": "bridge.log",
  "log_truncate_seconds": 300,
  "quiet": true,
  "menu": true
}
```

Адреса радио в поставке нет. `config.json` с вашими адресами в git не
попадает (он в `.gitignore`), в репозитории только `config.example.json`.
Привязка к телефону в конфиг не пишется вообще.

| поле | что это |
|---|---|
| `transport.kind` | `"tcp"` (Wi-Fi), `"serial"` (USB) или `"ble"` |
| `transport.target` | IP-адрес, `COM4` или BLE-адрес |
| `name` | ник моста, который видно в Bitchat |
| `chat` | беседа по умолчанию: `{"kind": "channel", "index": 1}`, `{"kind": "dm", "node": "A1B2"}` или `{"kind": "all"}` |
| `ble_scan_seconds` | длина одного прохода BLE-сканирования |
| `bitchat_target` | если указать BLE-адрес телефона — искать только его |
| `full_sync` | полная синхронизация сразу при старте |
| `bitchat_forward` | `bound`, `custom`, `replies` или `all` — см. меню `b` |
| `history_limit` | сколько последних сообщений держать с каждой стороны |
| `lora_send_interval` | пауза между отправками в LoRa, секунды |
| `lora_stale_seconds` | через сколько выкидывать залежавшееся из очереди |
| `log_file` | файл лога (по умолчанию почти пустой) |
| `log_truncate_seconds` | как часто обнулять лог |
| `quiet` | без подробных логов |
| `menu` | показывать стартовое меню |

Ещё флаги:

```bat
run.bat --host 192.0.2.10
run.bat --port COM4
run.bat --ble AA:BB:CC:DD:EE:FF
run.bat --chat all
run.bat --chat dm:A1B2
run.bat --history 200
run.bat --lora-interval 20
run.bat --debug
run.bat --test-send "проверка связи"
```

Флаги перекрывают конфиг. Если указан `--host`/`--port`/`--ble`, меню
выбора радио не показывается, но телефон всё равно подтверждается в
консоли — без терминала мост не стартует.

## Геочат, группы и личные сообщения

В LoRa они не пересылаются ни в одном режиме, и это не настройка, которую
можно снять.

| вид | как передаётся | доходит ли до моста |
|---|---|---|
| общий чат `#mesh` | broadcast по Bluetooth, открытым текстом | да |
| гео-канал | события Nostr через ретрансляторы в интернете | нет, по Bluetooth его нет |
| своя группа | кадр `0x25`, тело зашифровано ключом из keychain телефона | только шифртекст |
| личные сообщения | кадр `0x11`, Noise, ключ только у двух телефонов | только шифртекст |

Расшифровать без ключа из keychain нельзя. Поэтому если надо, чтобы
сообщение ушло в эфир, его пишут в общий чат.

Про геочат: два телефона в метре друг от друга не увидят друг друга в
геочате без интернета. Сообщение там — запись на ретрансляторе, а не
радиосигнал. Мост мог бы сам ходить на ретрансляторы, но это уже второй
клиент Bitchat со своими ключами и подписками, а не мост.

Открыть личный чат в Bitchat — нажать имя человека в списке «ЛЮДИ».

## Приватные каналы и подтверждения

Полная синхронизация и ручная отправка Bitchat → LoRa могут гнать трафик
в приватный канал радио. Поэтому первый раз за сеанс мост объясняет это
и просит два `yes`. Одно — отменяется. Дальше в этом сеансе не спрашивает;
`r` (сброс привязки) сбрасывает и это.

Публичные каналы — без вопросов.

## Как это устроено, коротко

* Компьютер — BLE-центр, телефон — периферия. Мост ищет сервис Bitchat,
  подключается, шлёт подписанный announce и слушает уведомления. Announce
  повторяется раз в минуту.
* Каждые 15 секунд короткий keepalive. Если телефон молчит 90 секунд или
  Windows сообщила об обрыве — соединение закрывается и открывается заново.
* Пока связь есть, Bluetooth не сканируется: сканирование отнимает время,
  за которое телефон должен ответить.
* Пакеты Bitchat: заголовок v1, подпись Ed25519, тело через zlib (иногда
  старый lz4). Фрагменты собираются, исходящие режутся по размеру пакета.
  peer id сверяется с Noise-ключом.
* Служебные типы (группы, Noise, файлы, голос, ретрансляция Nostr)
  отбрасываются сразу после заголовка, ещё до распаковки.
* Meshtastic — через библиотеку `meshtastic`: `sendText` и pubsub
  `meshtastic.receive`. Своё эхо отфильтровывается.

## Буферы и память

* В каждую сторону хранятся последние 100 сообщений.
* Очереди и история живут в памяти процесса. Перезапуск — всё пропало.
* В буфере лежит не текст, а зашифрованный блоб; открытым текст живёт
  только на время отправки.
* Пока мост работает, дамп процесса под обычной учётной записью снять
  нельзя, а аварийный дамп Windows за него не сохраняется. Это про процесс
  моста и больше ни про что.

> Пока телефон не подключён по Bluetooth, мост новых сообщений из Bitchat
> физически не получает — их неоткуда взять. Буфер спасает для случая
> «телефон на связи, а радио нет».

## Ограничения и странности

* Один телефон на запуск. Второму мост не даёт подключиться. Режимы
  `2`–`5` не открывают мост другим телефонам — они только решают, чьи
  сообщения, уже дошедшие до вашего телефона, пересылать дальше.
* Телефон должен быть рядом и Bitchat открыт. iOS в фоне перестаёт
  рекламироваться.
* iOS меняет BLE-адрес, Windows помнит старые. Поэтому в поиске мусор
  отсеивается проверкой подписи, а привязка держится по peer id и
  отпечатку ключа, а не по адресу.
* Кириллица в LoRa обычно работает, но зависит от настроек канала и
  клиентов на другой стороне.
* На ESP32 Wi-Fi и BLE взаимоисключающи: если радио доступно по Wi-Fi,
  пункт «Bluetooth» его не найдёт. Это нормально.
* Один TCP-порт 4403 обычно обслуживает одного клиента — не подключайтесь
  к радио другим TCP-клиентом одновременно с мостом.
* На живом трафике (проверено в ноябре 2026) клиент Bitchat передаёт по
  BLE в основном announce и requestSync. Чужие личные сообщения до
  компьютера вообще не доходят. Так что режимы `custom`/`all` на практике
  чаще всего дают то, что телефон сам решил разослать.

## Если не работает

* `--debug` — подробный лог. `bridge.log` по умолчанию почти пуст.
* `diag\tcp_probe.py <ip>` и `diag\mesh_probe.py COM4` — сырая проверка
  API Meshtastic без моста.
* BLE-пир не находится:
  1. Bluetooth включён, Bitchat открыт;
  2. телефон прислал announce — без него привязки не будет;
  3. в `--debug` видно, рекламируется ли нужный service UUID;
  4. на Linux пришлось бы настраивать BlueZ, на Windows не надо.

## Живая проверка

Запускаете `run.bat`, выбираете радио, подтверждаете телефон (два `yes`),
выбираете беседу. Дождались `[Bitchat] телефон подключён`.

Дальше:

1. Сообщение из LoRa от другого узла приходит в Bitchat от `MeshBridge`.
   В консоли — только `[LoRa] имя: сообщение (N симв.)`.
2. Пишете в Bitchat — в консоли `[Bitchat] имя: сообщение (N симв.)
   (в буфере, ждёт ручной синхронизации)`. `s` → `Bitchat → Meshtastic` →
   количество → отправить. В LoRa оно придёт как `[Бит: имя] текст`.
3. Унесите телефон или радио, подождите, верните. Мост должен подняться
   сам.
4. Поменяйте режимы `b` и посмотрите через `l`, что запомнилось после
   перезапуска.

## Проверки без телефона

не входят):

| скрипт | что проверяет |

| `full_sync_check.py` | полная синхронизация и `may_forward` |
| `config_check.py` | что режим сохраняется в `config.json` |
| `coverage_check.py` | что Python 3.14 не отрезал хвосты функций |
